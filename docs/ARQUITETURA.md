# Arquitetura simples para o recomeço
## Escolha proposta para o projeto novo
React + Vite + TypeScript no frontend; Express/TypeScript em uma API /api; Supabase Auth, PostgreSQL/RLS e Storage privados; GitHub e hospedagem Vercel elegível. É uma escolha de projeto sustentada pela referência inspecionada, não garantia de custo ou desempenho. Não migrar a aplicação atual: a base nova nasce em diretório/repositório e ambientes identificados, preservando a anterior.
O produto é principalmente autenticado; não há requisito confirmado que obrigue SSR. A SPA mantém navegação no cliente e pode usar React.lazy/Suspense para carregar editor, PDF e módulos apenas quando abertos. Servidor é necessário para segredos, validação confiável de arquivo, PDF oficial e operações administrativas. Sem chave secret/service_role no bundle ou variáveis VITE_*.
## Fluxo único
Tela → validação tipada → API do módulo → identidade verificada + operação autorizada → RLS/RPC transacional/Storage → resposta tipada → atualizar apenas região afetada. CRUD simples usa RLS e sessão do usuário; comandos críticos usam função de domínio atômica. Não fazer a mesma validação em três chamadas remotas antes de salvar. Validação de interface melhora experiência; servidor/banco continuam autoridade.
Um SDK Auth e um estado de sessão no frontend; um verificador no backend por request; estado/capacidade de negócio atual no banco por operação. Revalidação crítica após lock e antes de entrega; não cachear privilégio global. Login público não depende da validação de cookie antigo. SDK pode usar seu armazenamento oficial de sessão; proibir cópia manual de token, CPF, PDF ou dados de negócio em cache de PWA/localStorage.
## Organização sugerida, criada aos poucos
src/app/ contém router, providers e shell; src/ui/ contém LoadingState, EmptyState, ErrorState e FormFeedback; src/features/<dominio>/ contém página, formulário e acesso a dados daquele domínio. server/app.ts monta a API; server/modules/<dominio>/ contém router e regras de orquestração. shared/ contém schemas/contratos seguros que ambos usam. supabase/migrations/ e seed guardam banco e capacidades; tests/ recebe testes focados; docs/etapas/ guarda cartões e fechos curtos.
Manter um roteador convencional, um registro de menu e um catálogo de capacidades. Não copiar o App.tsx de1624 linhas do Horti nem seu mapa de rotas, catálogo, offline nativo, pacotes Capacitor ou pipeline extenso. Arquivo grande é sinal de revisão de responsabilidade, não obrigação de divisão arbitrária. Sem ORM, microserviço, evento distribuído ou fila externa antes de necessidade comprovada.
## Transporte e publicação
Na etapa02 comprovar o mesmo /api em dev, preview e hospedagem de teste. Vite sozinho serve frontend; vite preview sozinho não garante API. Usar adaptador Express/Function apropriado à versão atual e conferir documentação oficial. Não copiar rewrites antigos sem teste. API inexistente devolve JSON404; rota de página profunda devolve aplicação; /assets permanece estático.
Fixar Node compatível e versões/lockfile uma vez; npm ci reproduz. Scripts propostos: dev, build, preview, typecheck, lint, test e verificação focada por domínio. build compila; CI executa qualidade/segurança antes de promoção. Não embutir todas as baterias históricas em várias cadeias build→verify→build. Alteração documental não executa build/migração/deploy de produto.
## Erros e logs
Envelope seguro: data/meta ou error.code, message e request_id. Nunca retornar SQL, cookie, segredo, token, CPF integral ou conteúdo jurídico em log. 401 não autenticado,403 sem capacidade,409 conflito,422 validação,503 dependência indisponível. Estado vazio não é erro. Falha em grants internos não muda papel comercial nem deve abrir RLS como correção.
## Ambientes e restrições
Não reutilizar IDs/segredos/projetos antigos por conveniência. Definir destino novo antes de mutação e custo antes de criar serviço. Se a conta gratuita não comportar outro ambiente, usar local oficial/isolado e registrar limitação; não usar produção para fixtures. Hobby da Vercel é para uso pessoal não comercial: confirmar opção elegível antes de operação do escritório; não contratar automaticamente. Sem IA ou integrações bancárias automáticas iniciais.

## Contrato Auth implementado na 04

Browser usa somente chave publicável/anon e um SDK com PKCE; API recebe Bearer explícito e verifica getUser antes de RPC invoker my_access_context. Não há cookie próprio de autenticação; browser/Express não usam service_role. O SDK gerencia armazenamento/refresh; nenhuma cópia de token em cache de negócio/PWA. Respostas protegidas são privadas/no-store e não abrem CORS.

A autorização no banco também exige auth.sessions vigente pelo session_id do JWT. Somente helper privado lê sessões; as roles da API não recebem SELECT nelas. Perfil/vínculo/escritório/role/capacidade e confirmação/banimento continuam atuais em toda operação. Descoberta de contexto retorna somente escritórios próprios autorizados.

Cadastro mínimo passa por trigger privado transacional e gera somente client no escritório configurado por operador. Role/office em metadata são ignorados. Se cadastro estiver desabilitado ou sem escritório único, Auth pode criar credencial sem vínculo; não recebe acesso ao produto. Não há associação de acervo/CPF/e-mail. As quatro contas anteriores não são reclassificadas pelo trigger.

Callback troca código PKCE pelo SDK, limpa URL e usa destinos internos fixos. Marcador de recuperação em sessionStorage, limitado a15 min e session_id, restaura apenas o formulário após reload; não concede autorização nem substitui verificação do provedor. Atualização de senha continua autenticada pelo Supabase. SMTP/templates/MFA não foram alterados.

## Extensão de equipe implementada na05

`/api/team` verifica identidade uma vez e chama uma RPC de negócio que autoriza com estado atual; sem pré-consulta redundante de contexto. Quatro tabelas privadas com RLS guardam permissões individuais, identidade mínima, delegações e convites. Wrappers públicos invoker executam implementações privadas definer com search_path vazio e grants estreitos. Lock por escritório serializa mutações; identidade/e-mail e prazos são revalidados após esperas.

O envio usa Edge Function do próprio Supabase, com autenticação JWT da plataforma e getUser/RPC do caller. Apenas a chamada Auth admin e a conclusão estreita de delivery usam segredo automático do runtime; não há segredo na Vercel. Convites implicit passam pelo SDK oficial no callback apenas com UUID válido; cadastro/recuperação normais continuam PKCE. CPF bcrypt e fingerprint privada de alteração de senha não saem do banco. Conferência/aceite são transacionais e não associam acervo por e-mail.
